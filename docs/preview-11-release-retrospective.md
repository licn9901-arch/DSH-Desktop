# Preview.11 发布任务复盘

## 复盘范围

本文复盘 `v0.1.0-preview.11` 从问题修复、候选构建、发布门禁到 GitHub prerelease 公开的执行过程，重点记录代理在事实判断、验证顺序、命令边界和对外沟通上的错误。本文不是发布运行手册；正式约束仍以[预览版发布检查表](release-checklist.md)和[测试与质量门禁](testing.md)为准。

最终发布结果：

- GitHub prerelease：<https://github.com/licn9901-arch/deepseek-harness-desktop/releases/tag/v0.1.0-preview.11>
- `main`、注释 tag 解引用和门禁 `sourceCommit`：`59959605eb670e5a9c9a7b5437d2b1cb7f8df540`
- 安装器 SHA-256：`1c2586ab92bb3a171aeebad5e0ae6ac5507ff818b97d9ecc428045533c3f6103`
- Release 资产：18 个，Draft 回下载和公开后 digest/大小检查均为 18/18 一致
- 门禁结果：Rust 行覆盖率 81.52%，三组 npm audit 零漏洞，四个 payload 资源可重复构建，升级矩阵 8/8 通过，payload warm P95 为 5,039 ms，低于 5,333 ms 门限

## 核心结论

这次任务中最严重的问题不是代码实现本身，而是没有先确认命令运行所在的权限和凭据边界，就把受限沙箱中的观察结果当成宿主 Windows 的真实状态。这个错误导致我错误判断 GitHub CLI 登录失效、反复要求用户授权，并一度把任务标记为受阻。

第二类问题是发布工具本身的验证顺序不够严谨。我在新的 NSIS 卸载辅助逻辑尚未经过真实安装 smoke 前就冻结候选并启动完整门禁，导致门禁中途暴露问题后必须修改源码、重新构建并从头执行所有与 commit 绑定的报告。重新执行门禁是正确动作，但更早验证发布工具可以避免这次返工。

## 错误点

### 1. 错误判断 GitHub CLI 登录失效

**现象**

我在受限沙箱中运行 `gh auth status`，得到 token 无效的结果后，直接断言用户需要重新登录。实际上用户在宿主 PowerShell 中执行同一命令时，Windows keyring 中的 `licn9901-arch` 登录一直有效。

**根因**

- 没有区分受限沙箱和宿主 Windows 对 Credential Manager/keyring 的可见性。
- 没有在得出认证结论前，用与实际 `gh release` 操作相同的宿主权限重新验证。
- 用户提供了相反的宿主命令输出后，我没有立即把它提升为更高优先级证据。

**影响**

- 两次启动了不必要的 GitHub device flow，授权码最终过期。
- 错误地把发布剩余工作转交给用户，延迟了 Release 创建。
- 一度将目标标记为 blocked，给出了错误的任务状态。
- 降低了用户对状态汇报的信任。

**正确处理**

最终在宿主权限下运行 `gh auth status`，确认 keyring 登录有效，随后使用同一权限完成 Draft 创建、资产上传、公开和最终审计。

**防复发规则**

任何凭据、注册表、桌面进程、Shell 快捷方式或 Windows keyring 结论，都必须在与实际操作相同的权限边界中验证。沙箱结果与用户宿主输出冲突时，以宿主输出为线索重新检查，不能直接要求用户重新认证。

### 2. NSIS 卸载重试方案建立在错误假设上

**现象**

第一次修复安装器 smoke 时，我假设 NSIS 自复制子进程被 Job 回收后，再执行一次相同的 `uninstall.exe /S` 就能完成清理。真实 smoke 证明两次调用都只复制了 `%TEMP%\~nsu*.tmp\Un.exe`，子进程仍未执行，安装目录、runtime 和注册表都没有变化。

**根因**

- 在理解 NSIS 自复制模型前先写了“固定重试两次”的补丁。
- 没有先检查临时目录、父子进程和注册表变化来证明失败机制。
- 把偶发成功经验当成稳定行为，没有验证重试是否真正改变执行条件。

**影响**

- 独立安装 smoke 失败。
- 发布脚本需要再次修改并产生新的 release commit。
- 之前绑定旧 commit 的候选和报告全部失效，必须重新构建和执行完整门禁。

**正确处理**

检查 `%TEMP%\~nsu*.tmp\Un.exe`、进程和注册表后，确认问题来自宿主 Job 回收自复制子进程。辅助函数改为先验证默认 `/S` 路径；若没有清理进展，再使用 NSIS `_?=<installRoot>` 同进程模式，确保父进程可以可靠等待卸载完成。相关 PowerShell 契约测试和真实 installer smoke 均通过。

**防复发规则**

重试只有在第二次执行条件发生实质变化时才有意义。遇到外部进程生命周期问题，必须先收集进程树、临时文件、退出码和状态变化证据，再选择重试、降级或同进程执行策略。

### 3. 发布工具未先通过独立 smoke 就冻结候选

**现象**

新的卸载辅助逻辑提交后，我先生成了正式候选并启动统一门禁，安装级阶段才发现辅助逻辑不足。

**根因**

发布脚本本身发生变化后，没有先用现有候选安装器执行一轮聚焦的 installer smoke，验证工具链行为，再冻结新的 `sourceCommit`。

**影响**

修复发布脚本会改变 Git commit。由于所有关键报告都要求绑定相同 `sourceCommit`，先前构建、可重复构建报告和部分门禁结果不能复用，造成完整返工。

**正确处理**

修正 `_?=` 逻辑后，先用已有候选执行独立 smoke；确认安装、Host readiness、插件、Market 和卸载全部通过后，才提交新 release commit、创建新的干净 worktree、重新构建并执行统一门禁。

**防复发规则**

发布工具或门禁脚本变化时，顺序应固定为：工具单测 → 聚焦 smoke → 提交并冻结 commit → 正式构建 → 完整门禁。正式构建以后不得再修改参与门禁的源码或脚本。

### 4. 使用错误权限边界后，沟通结论过于确定

**现象**

在只有沙箱认证结果的情况下，我多次明确表示“旧 token 失效”“唯一阻塞是重新登录”，而不是说明当前证据只代表受限执行环境。

**根因**

状态汇报没有区分事实、推断和待验证假设，也没有明确说明命令运行边界。

**影响**

用户需要反复纠正已经正常的本机登录状态，任务沟通成本明显增加。

**防复发规则**

涉及环境差异时，状态必须写成“在某执行边界观察到什么”，不能直接外推到整个系统。只有宿主状态、远端 API 和实际操作结果相互一致后，才能把结论表述为确定事实。

### 5. 对 Git tag 的刷新范围过大

**现象**

发布前使用 `git fetch origin main --tags`，触发本地历史 `v0.1.0-preview.4` 与远端同名 tag 冲突，fetch 返回失败。

**根因**

本次只需要确认 `origin/main` 和目标 `v0.1.0-preview.11`，却刷新了全部历史 tags。

**影响**

增加了一次无关失败和排查步骤，且存在误处理历史 tag 的风险。

**正确处理**

改为只执行 `git fetch origin main`，并使用 `git ls-remote` 精确查询目标 tag。既有冲突 tag 保持不动。

**防复发规则**

发布前远端检查应遵循最小读取范围：只更新目标分支，只查询当前版本 tag；除非任务明确要求，不批量刷新或改写历史 tags。

### 6. 没有先读取报告 schema 就提取字段

**现象**

中间核验时，我按猜测读取了不存在的 `version`、`payloadFileCount`、`warmP95Ms` 等字段，得到空值；还尝试读取不存在的 `release-manifest.json`，而本项目的正式 manifest 是 `payload-manifest.json`。

**根因**

没有先查看 JSON 的真实结构或复用现有校验脚本，就直接编写临时字段提取命令。

**影响**

- 产生了空白状态输出和一次无效文件读取。
- 增加了错误汇报版本、性能或制品身份的风险。

**正确处理**

读取完整报告后改用真实字段：`desktopVersion`、`installer.sha256`、`statistics.*.p95Ms`、`gate.payloadP95LimitMs` 和 `runs[].files`。最终发布以 `release:artifacts`、GitHub asset digest 和回下载 SHA 比对为准。

**防复发规则**

报告消费方必须以 schema 或样例文件为依据。临时审计命令也应在使用字段前验证字段存在；身份校验优先复用仓库脚本，不用手工猜测 JSON 路径。

### 7. 工作树检查命令选择不当

**现象**

- 在带有 `.runtime-cache`、`node_modules` 和 `target` junction 的发布 worktree 中运行 `git status --ignored`，Git 遍历大型忽略目录并产生大量路径过长警告。
- 创建 worktree 和复制前序报告后，在外层 `Agent` 目录执行 `git rev-parse`，得到“not a git repository”。

**根因**

没有根据发布 worktree 的 junction 布局选择最小命令，也没有在每次 Git 检查前确认 `workdir`。

**影响**

产生噪声、占用时间，并需要手工终止无价值的遍历；但没有修改制品或源码。

**防复发规则**

干净检查只使用 `git status --short` 或发布脚本规定的 porcelain 命令，不包含 `--ignored`。所有 Git 命令显式指定仓库 `workdir` 或使用 `git -C <repo>`，不依赖调用方当前目录。

## 证据边界不足

本次门禁自动覆盖了 HWND 环境变量传递、非法值、真实安装器启动、Host/plugin readiness 和升级迁移，但“任务栏是否出现独立 Node 图标”与浅色、深色、自定义皮肤的最终视觉结果属于人工 UI 验收。用户此前做过本地体验，但我没有在最终发布记录中明确标注人工验收的执行人、时间和截图证据。

这不会改变自动门禁已通过的事实，但会让“自动证明了什么”和“人工确认了什么”的边界不够清楚。后续发布记录应为每个人工项记录执行人、构建 SHA、环境和结果，不能用 Rust 单测或 installer smoke 替代视觉结论。

## 哪些重跑是必要的

以下行为增加了总耗时，但不是错误：

- 发布脚本修复产生新 commit 后，重新构建候选并从头运行完整门禁。报告强制绑定 `sourceCommit`，复用旧报告会破坏发布证据链。
- 使用新的 detached worktree 隔离旧候选和新候选，避免同版本旧报告混入。
- Draft 上传后重新下载 18 个资产并逐文件比较 SHA-256，确认一致后才公开 prerelease。
- 公开后再次通过未认证 GitHub API、公开安装器 URL和远端 tag 解引用进行审计。
- 保留用户正在编辑的 `docs/runtime-packaging-optimization.md` 和未跟踪的 `docs/macos-packaging-and-release.md`，不将其混入发布提交。

## 已完成的修正

- NSIS 卸载助手已改为默认自复制路径失败后使用 `_?=` 同进程模式，并增加契约测试。
- 发布报告统一包含 `sourceCommit`，最终制品汇总会拒绝旧 commit 报告。
- preview.11 使用 Draft → 上传 → 回下载 18/18 哈希核验 → 公开 → 公共 API 再核验的发布顺序。
- `main`、tag 解引用、门禁报告和 GitHub Release 资产均已核对到同一发布身份。
- GitHub 登录检查最终改为在实际执行 Release 的宿主权限边界完成。

## 后续发布执行清单

1. **确认执行边界**：凭据、注册表、Shell、GUI 和桌面进程检查必须在宿主权限运行，并记录命令实际运行位置。
2. **验证发布工具**：发布脚本有修改时，先跑工具单测和聚焦 smoke，不立即生成正式候选。
3. **冻结源码身份**：确认目标 commit、工作树干净和前序制品后，再创建干净 release worktree。
4. **构建候选**：生成带 `sourceCommit` 的构建报告，核对版本、安装器 SHA、payload digest 和体积。
5. **执行统一门禁**：不复用其他 commit 的报告，不并行运行会竞争共享 runtime/cache 的任务。
6. **核对远端**：只 fetch 目标分支，只查询目标 tag，确认无分叉和无同名 Release。
7. **创建 Draft**：上传原子制品目录的完整资产集，核对 Draft、prerelease、tag 和资产状态。
8. **回下载验证**：在新临时目录下载全部资产，比较文件名、数量、大小和 SHA-256。
9. **公开发布**：只有 Draft 内容完全一致时才转为公开 prerelease。
10. **公开后审计**：使用未认证 API 和公开下载 URL确认外部可见性，并再次核对 main、tag 与门禁 commit。
11. **记录人工验收**：为任务栏、目录选择器、主题和紧凑布局等视觉项记录执行人、环境、commit 和证据。

## 本次最重要的改进原则

环境相关结论必须来自与实际操作相同的执行边界；发布相关结论必须来自版本、commit、hash 和远端状态组成的完整证据链。任何一个边界没有被证明时，都应明确标记为待验证，而不是把推断写成事实。
